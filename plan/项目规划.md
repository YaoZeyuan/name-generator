# 项目规划

本文档用于沉淀「诗云-起个好名字」的项目规划。后续我们优先通过本文档迭代需求、范围和实现路径。

约定：

- `@todo(yao)` 表示需要 yao 确认、取舍或补充的信息。
- 已确认的内容移动到「已确认决策」或删除 `@todo(yao)` 标记。
- 本项目不以商业化为目标，核心目标是实际解决起名问题。

## 1. 项目想解决什么问题

项目要解决的问题不是「随机生成很多名字」，而是：

> 让用户输入姓氏和必要约束后，在很短时间内得到一小批值得认真挑选、读音顺、来源可信、能解释的三字姓名。

当前起名过程的痛点：

1. 候选来源分散，不知道从哪里找可靠名字。
2. 随机组合噪声太大，会产生无意义、难听或有歧义的名字。
3. 人工筛选成本高，海量候选反而让用户更难决策。
4. 音韵、避讳、多音字、辈分字、字义、字形等约束分散，用户很难系统检查。
5. 好名字需要解释，用户需要知道「为什么这个名字值得考虑」。

成功标准：

1. 用户能在 60 秒内得到 20 到 50 个高质量候选名。
2. 每个候选名至少给出基础解释：来源、音律结果、用字频率或推荐理由。
3. 用户可以输入姓氏、避讳字、指定字和指定位置。
4. 系统默认避开明显风险：多音字、同音冲突、音韵拗口、过于生僻的字、明显负面词。
5. 输出结果足够少，能直接进入人工挑选，而不是继续让用户面对几千条列表。

非目标：

1. 不承诺自动找到「唯一最好的名字」。
2. 不替代父母或使用者的最终审美判断。
3. 不优先做商业化、营销页或流量功能。
4. 不优先做八字、生肖、五行等传统命理能力。@todo(yao) 请确认这类能力是否明确排除，还是保留为远期可选项。
   1. @todo(codex) 确认，不做这些传统命理能力支持。只解决可以量化的三件事
      1. 音律得当
      2. 绕过避讳
      3. 最好有含义

## 2. 项目打算如何解决

项目应采用「从高质量既有名字中筛选和重组」作为主线，而不是把所有汉字随机排列组合。

核心判断：

1. 好名字大概率已经在历史、现代姓名、字号、文学化词语、机构命名中出现过。
2. 项目要做的是「好名字的搬运、筛选、解释和排序」。
3. 枚举所有可能组合的「诗云」方案保留为辅助能力，但不作为默认推荐主线。

推荐主流程：

```text
输入约束
  -> 载入候选二字名库
  -> 换上目标姓氏
  -> 硬过滤
  -> 分项评分
  -> 排序去重
  -> 输出少量候选
  -> 用户收藏或排除
  -> 继续推荐相似名字
```

已有数据资产：

| 名库          | 用途                       | 当前判断                               |
| ------------- | -------------------------- | -------------------------------------- |
| 古人云        | 古人姓名与字，有典故倾向   | 高质量，适合作为文化来源               |
| 登科录        | 历代进士姓名、字号、别号   | 规模大，有历史感，但需过滤古旧表达     |
| 五道口-精选集 | 科研基金负责人、两院院士等 | 现代、稳重，适合作为主推荐来源         |
| 五道口-集思录 | CNKI 项目负责人            | 规模大，适合补充候选                   |
| 他山石        | 现代公开姓名               | 贴近现实，但来源解释较弱               |
| 财富论-精选集 | 私募基金和公司名中的二字词 | 有词感和寓意，但不像人名，需要更强过滤 |
| 财富论-集思录 | 低频基金词                 | 适合灵感探索，不适合默认高权重         |

## 3. 好名字的判断框架

建议把「好名字」拆成可计算、可解释的几个维度：

1. 来源质量：名字来自什么库，是否有典故、人物、词语或统计支持。
2. 音律质量：姓与名连读是否顺，是否避开同音、同调、叠声、叠韵。
3. 用字质量：是否常见、是否适合做人名、是否有多音风险。
4. 语义安全：是否包含明显负面字、歧义词、网络梗、低俗谐音。
5. 稀有度：不过分大众，也不过分生僻。
6. 字形观感：笔画是否过于悬殊，结构是否协调。
7. 可解释性：是否能给用户一个可信的推荐理由。

建议评分结构：

```text
总分 = 来源分 + 音律分 + 用字分 + 语义安全分 + 稀有度分 + 字形分 + 可解释性加分
```

第一版可以先做轻量评分，不依赖大模型：

| 维度     | 第一版实现                     |
| -------- | ------------------------------ |
| 来源质量 | 按名库设定基础权重             |
| 音律质量 | 复用旧版声母、韵母、音调规则   |
| 用字质量 | 复用已有字频、多音字、标准字库 |
| 语义安全 | 维护人工黑名单和风险词表       |
| 稀有度   | 以字频和候选名频率估算         |
| 字形观感 | 暂缓或只做笔画差距             |
| 可解释性 | 展示来源、规则命中情况         |

## 4. 具体需要哪些步骤

目标：让当前仓库进入可开发状态。

任务：

2. 把旧版 `old/src`、`old/script`、`old/database` 中可复用代码迁移到根目录工程。
3. 修正当前入口断裂问题：根目录 `index.html` 指向 `/index.tsx`，但根目录没有 `index.tsx`。
4. 修正脚本路径：`package.json` 指向 `script/...`，但实际主要脚本在 `old/script/...`。
5. 去除或修正旧脚本中的本机硬编码路径。

### 阶段二：生成统一候选名数据库

目标：把旧版散落的字符串名库升级为结构化候选名库。

候选名记录至少包含：

1. `name`：二字名，如 `子衿`。
2. `sources`：来源列表，如 `古人云`、`登科录`。
3. `sourceReasons`：来源说明或关联人物。
4. `chars`：两个字的拼音、声母、韵母、声调、字频、多音字标记。
5. `flags`：是否含风险字、是否过生僻、是否可解释。
6. `score`：分项评分和总分。

第一版输出：

```text
database/candidate/candidate_name_db.json
database/candidate/candidate_char_db.json
database/candidate/source_index.json
```

@todo(yao) 请确认数据库输出目录是否使用 `database/candidate/`。

### 阶段三：实现命令行验证器

目标：先不用 Web，用 CLI 验证推荐质量。

示例命令：

```bash
pnpm name --surname 张 --gender male --avoid 李诞,呼兰 --must 子 --must-pos 2 --limit 30
```

示例输出字段：

| 字段     | 示例                           |
| -------- | ------------------------------ |
| 姓名     | 张子衿                         |
| 总分     | 86                             |
| 来源     | 古人云、登科录                 |
| 音律     | 姓名三字声调组合较顺，未叠韵   |
| 用字     | 两字均为常见人名用字           |
| 风险     | 未发现明显风险                 |
| 推荐理由 | 有文化来源，读音清晰，字形简洁 |

@todo(yao) 请确认第一版 CLI 输出数量默认是 30 个还是 50 个。

### 阶段四：实现 Web 界面

目标：把 CLI 已验证的推荐能力接到前端。

第一版 Web 不做复杂页面，只做一个高效工具界面：

1. 输入姓氏。
2. 输入避讳字或亲属姓名。
3. 输入指定字和位置。
4. 选择偏男宝、偏女宝、都看看。
5. 选择来源偏好。
6. 展示推荐列表。
7. 支持收藏、不喜欢、换一批、导出。
8. 点击候选名查看解释。

@todo(yao) 请确认前端是否继续保留「偏男宝/偏女宝」这个说法，还是改成「响亮/柔和/不限」这类更中性的表达。

### 阶段五：偏好学习和相似推荐

目标：用户收藏几个名字后，系统能推荐风格相似的名字。

第一版可不做 embedding，只做规则相似：

1. 相同来源。
2. 相近声调模式。
3. 相似字频区间。
4. 相同用字风格标签。

## 5. 如何实现

建议目录结构：

```text
src/
  core/
    char.ts
    pinyin.ts
    phoneticRules.ts
    nameRules.ts
    scoreName.ts
    queryName.ts
    explainName.ts
  data/
    loadCandidateDb.ts
  cli/
    name.ts
  web/
    App.tsx

scripts/
  buildCharDb.ts
  buildCandidateNameDb.ts
  validateNameDb.ts

database/
  candidate/
    candidate_name_db.json
    candidate_char_db.json
    source_index.json
```

核心模块职责：

| 模块                      | 职责                                   |
| ------------------------- | -------------------------------------- |
| `phoneticRules.ts`        | 判断同音、同调、叠声、叠韵、音调评分   |
| `nameRules.ts`            | 处理避讳字、指定字、指定位置、多音字   |
| `scoreName.ts`            | 汇总来源、音律、用字、稀有度、风险评分 |
| `queryName.ts`            | 根据用户输入筛选、排序、分页           |
| `explainName.ts`          | 把评分结果转成用户可读解释             |
| `buildCandidateNameDb.ts` | 从各来源构建结构化候选名数据库         |
| `validateNameDb.ts`       | 检查候选库质量和异常数据               |

实现优先级：

1. 先迁移旧版可用的拼音和音韵规则。
2. 再生成统一候选名库。
3. 再做 CLI 查询。
4. CLI 推荐质量稳定后再做 Web。
5. 最后做收藏、相似推荐、大模型辅助。

## 6. 已确认决策

1. 项目不关心商业化，目标是实际解决起名问题。
2. 项目核心对象是三字姓名，即「姓 + 两字名」。
3. 项目已有数据和旧版实现，应优先复用，不从零开始。
4. 默认方向应从「生成更多名字」转向「筛出更少、更好、更可解释的名字」。
