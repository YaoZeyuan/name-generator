# 项目规划

本文档用于沉淀「诗云-起个好名字」的项目规划。后续我们优先通过本文档迭代需求、范围和实现路径。

约定：

- `@todo(yao)` 表示需要 yao 确认、取舍或补充的信息。
- 已确认的内容移动到「已确认决策」。
- 本项目不以商业化为目标，核心目标是实际解决起名问题。

## 1. 项目想解决什么问题

项目要解决的问题不是「随机生成很多名字」，而是：

> 让用户输入姓氏和必要约束后，在很短时间内得到一小批值得认真挑选、读音顺、能避开风险、最好有含义的三字姓名。

核心目标收束为三件可量化的事：

1. 音律得当。
2. 绕过避讳。
3. 最好有含义。

当前起名过程的痛点：

1. 候选来源分散，不知道从哪里找可靠名字。
2. 随机组合噪声太大，会产生无意义、难听或有歧义的名字。
3. 人工筛选成本高，海量候选反而让用户更难决策。
4. 音韵、避讳、多音字、辈分字、字义、字形等约束分散，用户很难系统检查。
5. 好名字需要解释，用户需要知道「为什么这个名字值得考虑」。

成功标准：

1. 用户能在 60 秒内得到 20 到 50 个候选名，第一版默认输出 30 个。
2. 每个候选名至少给出基础解释：来源、音律结果、用字频率或推荐理由。
3. 用户可以输入姓氏、避讳字、指定字和指定位置。
4. 系统默认避开明显风险：多音字、同音冲突、音韵拗口、过于生僻的字、明显负面词。
5. 输出结果足够少，能直接进入人工挑选，而不是继续让用户面对几千条列表。

非目标：

1. 不承诺自动找到「唯一最好的名字」。
2. 不替代父母或使用者的最终审美判断。
3. 不优先做商业化、营销页或流量功能。
4. 不做八字、生肖、五行等传统命理能力。
5. 不做 embedding 和大模型推荐。

## 2. 项目打算如何解决

项目采用「从高质量既有名字中筛选和重组」作为主线，而不是把所有汉字随机排列组合。

核心判断：

1. 好名字大概率已经在历史、现代姓名、字号、文学化词语、机构命名中出现过。
2. 项目要做的是「好名字的搬运、筛选、解释和排序」。
3. 枚举所有可能组合的「诗云」方案保留为辅助能力，但不作为默认推荐主线。

推荐主流程：

```text
输入约束
  -> 载入候选二字名库
  -> 换上目标姓氏
  -> 硬过滤
  -> 分项评分
  -> 排序去重
  -> 输出少量候选
  -> 用户标记喜爱/不确定/排除
  -> 导出评价结果，辅助后续筛选
```

已有数据资产：

| 名库          | 用途                       | 当前判断                             |
| ------------- | -------------------------- | ------------------------------------ |
| 财富论-精选集 | 私募基金和公司名中的二字词 | 默认优先，词感较现代，但需要强过滤   |
| 财富论-集思录 | 低频基金词                 | 灵感补充，排在精选集之后             |
| 五道口-精选集 | 科研基金负责人、两院院士等 | 现代、稳重，适合作为主推荐来源       |
| 五道口-集思录 | CNKI 项目负责人            | 规模大，适合补充候选                 |
| 他山石        | 现代公开姓名               | 贴近现实，但来源解释较弱             |
| 登科录        | 历代进士姓名、字号、别号   | 有历史感，但越古旧越需要过滤现代语感 |
| 古人云        | 古人姓名与字，有典故倾向   | 文化来源强，但默认优先级较低         |

默认来源优先级：

```text
财富论-精选集
  -> 财富论-集思录
  -> 五道口-精选集
  -> 五道口-集思录
  -> 他山石
  -> 登科录
  -> 古人云
```

原因：越古旧的名字越可能不符合现代含义或现代语感，所以古人类来源应保留文化价值，但不作为默认最高权重。

## 3. 好名字的判断框架

评价维度按重要度排序：

1. 语义安全。
2. 音律质量。
3. 来源质量。
4. 可解释性。
5. 用字质量。
6. 稀有度。

第一版评分策略：

| 维度     | 第一版实现                                       |
| -------- | ------------------------------------------------ |
| 语义安全 | 人工黑名单、风险词表、明显负面组合、明显俗套组合 |
| 音律质量 | 复用旧版声母、韵母、声调规则                     |
| 来源质量 | 按名库设定基础权重，支持同名多来源叠加           |
| 可解释性 | 展示来源、规则命中情况、推荐理由                 |
| 用字质量 | 复用已有字频、多音字、标准字库                   |
| 稀有度   | 以字频和候选名频率估算                           |

第一版不依赖大模型，用规则和数据先跑通。

建议评分结构：

```text
总分 = 语义安全分 + 音律分 + 来源分 + 可解释性分 + 用字分 + 稀有度分
```

硬过滤优先于评分。若命中严重风险，不参与排序。

### 评价样例

正向样例：

| 名字   | 参考价值                   |
| ------ | -------------------------- |
| 姚瑾瑞 | 现代、轻快、读音有辨识度   |
| 钱弘俶 | 有历史来源，庄重，有文化感 |
| 尧歌游 | 意象自由，有文学感         |

反向样例：

| 名字   | 问题                                   |
| ------ | -------------------------------------- |
| 赵钱孙 | 过于像《百家姓》前三字，像占位符       |
| 刘强   | 过于常见，且不是本项目主目标的三字姓名 |
| 李建国 | 时代感过强，俗套感明显                 |

这些样例用于后续验证评分方向，不代表最终黑白名单。

## 4. 工程规划

当前项目已初始化 Taro 4 + Vue 3。后续前端以 Taro 为底层框架，支持 H5 和微信小程序。

工程分为两部分：

1. 原始数据和清洗管线。
2. 界面展示和用户交互。

### 原始数据和清洗管线

1. 原始数据保存在 `resource/`，不移动。
2. 清洗后的数据放在 `database/`，格式为 JSON 和 README 文档。
3. 通过 `scripts/` 清洗 `resource/` 中的数据，输出到 `database/`。
4. 后续可以借助 GitHub 仓库托管到 Vercel，使 `https://name-generator.yaozeyuan.online/` 域名下可读取对应 JSON，实现数据动态更新。

### 界面展示

1. `src/` 仅作为 Taro/Vue 前端目录。
2. 前端本地开发通过 localhost 或代理读取本地 JSON。
3. 线上通过 `https://name-generator.yaozeyuan.online/` 读取托管的 JSON 资源。
4. 不依赖外部数据库。
5. 用户状态通过 URL 参数和本地存储保存。
6. 用户可以对名字标记：喜爱、不确定、排除。
7. 支持导出用户评价结果，方便后续人工筛选。

## 5. 目录结构

由于 `src/` 需要服务 Taro 小程序和 H5，平台无关核心逻辑不放入 `src/`，避免被前端框架耦合。

建议目录：

```text
packages/
  name-core/
    src/
      char.ts
      pinyin.ts
      phoneticRules.ts
      nameRules.ts
      scoreName.ts
      queryName.ts
      explainName.ts
      types.ts
    package.json
    tsconfig.json

scripts/
  buildCharDb.ts
  buildCandidateNameDb.ts
  validateNameDb.ts
  queryNameByConfig.ts

config/
  name-query.example.json

database/
  candidate/
    candidate_name_db.json
    candidate_char_db.json
    source_index.json
    README.md

src/
  app.ts
  app.config.ts
  pages/
    index/
      index.vue
      index.config.ts
```

核心模块职责：

| 模块                      | 职责                                       |
| ------------------------- | ------------------------------------------ |
| `phoneticRules.ts`        | 判断同音、同调、叠声、叠韵、音调评分       |
| `nameRules.ts`            | 处理避讳字、指定字、指定位置、多音字       |
| `scoreName.ts`            | 汇总语义安全、音律、来源、用字、稀有度评分 |
| `queryName.ts`            | 根据用户输入筛选、排序、分页               |
| `explainName.ts`          | 把评分结果转成用户可读解释                 |
| `buildCandidateNameDb.ts` | 从各来源构建结构化候选名数据库             |
| `validateNameDb.ts`       | 检查候选库质量和异常数据                   |
| `queryNameByConfig.ts`    | 读取 JSON 配置，输出推荐结果               |

## 6. 具体步骤

### 阶段一：工程整理

目标：让仓库进入可持续开发状态。

任务：

1. 保留 Taro 4 + Vue 3 作为前端框架。
2. 保留 `resource/` 作为原始数据目录。
3. 创建 `packages/name-core/` 存放平台无关核心逻辑。
4. 创建或整理 `scripts/`，承载数据清洗和 CLI 验证脚本。
5. 创建 `database/candidate/`，承载统一候选名库。
6. 把 `old/` 中可复用逻辑作为参考迁移，不直接依赖旧工程。
7. 清理或隔离旧 Vite/React 相关入口和脚本，避免和 Taro 工程混淆。

### 阶段二：生成统一候选名数据库

目标：把旧版散落的字符串名库升级为结构化候选名库。

候选名记录至少包含：

1. `name`：二字名，如 `瑾瑞`。
2. `sources`：来源列表，如 `财富论-精选集`、`五道口-精选集`。
3. `sourceReasons`：来源说明或关联记录。
4. `chars`：两个字的拼音、声母、韵母、声调、字频、多音字标记。
5. `flags`：是否含风险字、是否过生僻、是否可解释。
6. `score`：分项评分和总分。

第一版输出：

```text
database/candidate/candidate_name_db.json
database/candidate/candidate_char_db.json
database/candidate/source_index.json
database/candidate/README.md
```

### 阶段三：实现 JSON 配置式 CLI 验证器

目标：先不用 Web，用配置文件验证推荐质量。

示例配置：

```json
{
  "surname": "姚",
  "avoid": ["赵钱孙", "刘强", "李建国"],
  "must": [],
  "mustPosition": "any",
  "style": "any",
  "sourcePreference": "default",
  "limit": 30
}
```

示例输出字段：

| 字段     | 示例                   |
| -------- | ---------------------- |
| 姓名     | 姚瑾瑞                 |
| 总分     | 86                     |
| 来源     | 财富论-精选集          |
| 音律     | 姓名三字未同音、未叠韵 |
| 用字     | 两字均为可接受人名用字 |
| 风险     | 未发现明显风险         |
| 推荐理由 | 读音轻快，现代感较强   |

阶段验收：

1. 能基于 JSON 配置输出 Top 30。
2. 输出结果包含分项评分和解释。
3. 反向样例能被过滤或显著降权。
4. 正向样例的评分方向能解释得通。

### 阶段四：实现 Taro 前端界面

目标：把 CLI 已验证的推荐能力接到前端。

第一版界面能力：

1. 输入姓氏。
2. 输入避讳字或亲属姓名。
3. 输入指定字和位置。
4. 选择「响亮 / 柔和 / 不限」，并说明分别大致对应偏男宝、偏女宝、不限。
5. 选择来源偏好。
6. 展示推荐列表。
7. 支持标记「喜爱 / 不确定 / 排除」。
8. 支持换一批。
9. 支持导出候选名和评价结果。
10. 点击候选名查看解释。

### 阶段五：人工筛选辅助

目标：不用 embedding 和大模型，也能帮助用户缩小范围。

能力：

1. 导出候选名。
2. 导出用户评价。
3. 根据「喜爱 / 不确定 / 排除」隐藏或排序候选。
4. 按来源、音律、风险、字频过滤。

## 7. 已确认决策

1. 项目不关心商业化，目标是实际解决起名问题。
2. 项目核心对象是三字姓名，即「姓 + 两字名」。
3. 项目已有数据和旧版实现，应优先复用，不从零开始。
4. 默认方向从「生成更多名字」转向「筛出更少、更好、更可解释的名字」。
5. 不做八字、生肖、五行等传统命理能力。
6. 第一版不依赖大模型，只用规则评分。
7. 不考虑 embedding 和大模型推荐。
8. 默认来源优先级为：财富论、五道口、他山石、登科录、古人云；精选集在集思录之前。
9. 数据库输出目录使用 `database/candidate/`。
10. 第一版 CLI 默认输出 30 个候选名。
11. 前端倾向选择使用「响亮 / 柔和 / 不限」，并解释其与偏男宝、偏女宝、不限的关系。
12. `src/` 只作为 Taro/Vue 前端目录，核心逻辑放入 `packages/name-core/`。
13. CLI 采用 JSON 配置文件，方便调试和复现。
