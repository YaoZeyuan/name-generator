# 数据处理规划

本文档用于规划如何从 `resource/` 中的原始数据生成 `api/database/` 中可被推荐系统使用的 JSON 数据。

目标不是一次性写死某个脚本，而是建立一套可扩展的数据处理规范：后续新增数据源时，只需要补一个数据源适配器和少量配置，就能进入统一候选名库。

约定：

- `@todo(yao)` 表示需要 yao 确认、取舍或补充的信息。
- 原始数据保留在 `resource/`，不移动、不覆盖。
- 清洗结果输出到 `api/database/`。
- 脚本优先使用 TypeScript 编写，执行方式统一使用 `tsx scripts/...`；当前 `package.json` 已包含 `tsx` 开发依赖。

## 0. 开工结论

当前信息已经足够开展第一阶段数据管线实现，不需要再等待额外确认。

第一阶段按以下实施默认开工：

1. 使用 TypeScript 编写数据脚本，并用 `tsx` 执行。
2. 采用 `api/database/source/`、`api/database/extracted/`、`api/database/candidate/` 三层输出。
3. 先保留可追溯 `sourceRefs`，以便解释候选名来源；若后续 JSON 体积明显影响使用，再拆成索引文件。
4. 单字名不直接作为推荐候选，但纳入字频、用字质量和文化字权重统计。
5. 登科录第一版只启用姓名尾二字和「字」，别号、曾用名先不参与候选。
6. 五道口读取四个细分文件并保留来源层级，`汇总.txt` 只作为校验参考，不重复计数。
7. 财富论基金名和公司名不拆成两个最终来源，但在 `sourceDetail` 中保留文本类型。
8. 新数据源必须配套来源说明，至少描述来源、授权、更新时间和字段含义。

当前没有阻断开工的 `@todo(yao)`；后续需要 yao 判断的内容，主要会来自第一轮数据生成后的样本抽查和 Top 30 推荐结果。

## 1. 要解决的问题

当前第一版候选库是从 `old/database` 生成的，这能快速验证推荐流程，但长期不够理想。

真正的数据管线应该是：

```text
resource 原始数据
  -> source adapter 按来源解析
  -> normalized source records 标准化来源记录
  -> extracted name tokens 抽取二字候选
  -> candidate name db 统一候选名库
  -> query / score / explain 推荐系统使用
```

这套流程需要解决四件事：

1. 我们需要哪些字段。
2. 从 `resource/` 中可以提取哪些字段。
3. 每类数据源如何编写提取脚本。
4. 如何编订规范，方便后续补充新数据。

## 2. 输出数据分层

建议不要直接从原始数据一步生成最终候选名库，而是分三层输出。

### 2.1 来源记录层

目录建议：

```text
api/database/source/
  source_manifest.json
  wealth.records.json
  academic.records.json
  modern_people.records.json
  imperial_exam.records.json
  ancient_names.records.json
```

作用：

1. 保存每条原始记录的标准化结果。
2. 保留来源索引，便于回溯候选名为什么出现。
3. 为后续解释、审计和重新生成候选名提供依据。

建议字段：

```ts
type NormalizedSourceRecord = {
  id: string;
  sourceId: string;
  sourceLabel: string;
  sourcePath: string;
  rawIndex: number;
  rawText?: string;
  rawFields?: Record<string, unknown>;
  normalizedFields: Record<string, string | number | string[] | null>;
  extractedTexts: ExtractedText[];
};

type ExtractedText = {
  text: string;
  textType:
    | "person_full_name"
    | "given_name"
    | "courtesy_name"
    | "alias"
    | "fund_name"
    | "company_name"
    | "word_segment"
    | "science_person_name";
  confidence: number;
  note?: string;
};
```

### 2.2 候选片段层

目录建议：

```text
api/database/extracted/
  name_tokens.json
  rejected_tokens.json
  token_frequency.json
```

作用：

1. 保存从来源记录中抽出的二字候选。
2. 记录候选来自哪些来源、出现多少次、如何抽取。
3. 记录被拒绝的数据及原因，方便调规则。

建议字段：


```ts
type ExtractedNameToken = {
  // 抽取出的二字候选，例如「瑾瑞」。
  token: string;

  // 候选长度。正常应为 2；保留该字段便于记录异常和校验。
  tokenLength: number;

  // 该候选出现过的来源 ID 列表，例如 modern_people、ancient_names。
  sourceIds: string[];

  // 可追溯的来源引用。用于解释「这个候选为什么出现」。
  sourceRefs: SourceRef[];

  // 候选片段类型，用于区分它来自现代名、古人字、基金词等。
  tokenType:
    | "given_name"
    | "courtesy_name"
    | "alias"
    | "fund_word"
    | "company_word"
    | "modern_given_name"
    | "science_given_name";

  // 候选在来源中的出现次数；同一 token 合并后累计。
  frequency: number;

  // 抽取方法，用于审计和后续调权。
  extractionMethod:
    | "take_given_name"
    | "take_name_tail"
    | "split_alias"
    | "jieba_segment"
    | "word_frequency"
    | "manual";

  // 抽取可信度，范围建议为 0 到 1；结构化姓名来源高于分词来源。
  confidence: number;

  // 如果候选被拒绝，记录枚举化原因；正常入库候选为空。
  rejectReasons?: string[];
};

type SourceRef = {
  // 来源 ID。
  sourceId: string;

  // 标准化来源记录 ID。
  recordId: string;

  // 原始数据中的行号或数组下标。
  rawIndex: number;

  // 来自原始记录的哪个字段。
  field: string;

  // 触发抽取的原始值。
  value: string;
};
```

### 2.3 候选名库层

目录建议沿用当前结构：

```text
api/database/candidate/
  candidate_name_db.json
  candidate_char_db.json
  source_index.json
  README.md
```

当前第一版已经有这些文件。后续应把输入从 `old/database` 切到 `api/database/extracted/name_tokens.json`。

建议字段：

```ts
type CandidateNameRecord = {
  name: string;
  chars: [string, string];
  sourceIds: string[];
  sourceRefs: SourceRef[];
  sourceStats: {
    totalFrequency: number;
    sourceCount: number;
    bestSourcePriority: number;
  };
  tags: string[];
  flags: {
    hasRareChar: boolean;
    hasPolyphone: boolean;
    hasRiskChar: boolean;
    isLikelyNonNameWord: boolean;
  };
};
```

已确认：第一版可以继续把 `sourceRefs` 放入候选名库，先保证来源解释完整；如果后续 JSON 体积影响加载或调试，再拆成单独索引文件。


## 3. 当前 resource 可提取字段

### 3.1 现代姓名：他山石

文件：

```text
resource/person_name/已知人名.json
```

当前结构：

```json
{
  "木尔": {
    "name": "木尔",
    "counter": 1,
    "length": 2
  }
}
```

可提取字段：

| 字段       | 含义               | 用途         |
| ---------- | ------------------ | ------------ |
| key / name | 已整理出的名字片段 | 候选二字名   |
| counter    | 出现次数           | 频率、稀有度 |
| length     | 名字长度           | 过滤二字名   |

提取策略：

1. 只取 `length === 2` 的记录。
2. `name` 必须是两个合法中文字符。
3. 经过字库合法性、多音字、音律规则过滤。
4. 输出为 `modern_given_name`。

已确认：

1. 这个文件里的 key / name 已经是「名」，不是完整姓名。
2. 单字名不进入二字候选，但需要纳入字频统计，用于后续提供名字用字分布和用字质量参考。

### 3.2 古人名与字：古人云

文件：

```text
resource/old_person_name/中国古代人名与字-9336条-简体-opencc转换稿_手工替换_乾干.json
```

样例：

```json
{
  "raw_name": "乙瑛",
  "char_姓氏": "乙",
  "char_名": "瑛",
  "char_字": "仲卿"
}
```

可提取字段：

| 字段      | 含义     | 用途               |
| --------- | -------- | ------------------ |
| raw_name  | 原始姓名 | 来源解释           |
| char_姓氏 | 姓氏     | 校验姓名拆分       |
| char_名   | 名       | 候选名，若长度为 2 |
| char_字   | 字       | 候选名，若长度为 2 |

提取策略：

1. `char_名` 长度为 2 时作为候选。
2. `char_字` 长度为 2 时作为候选。
3. 保留 `raw_name` 作为来源解释。
4. 单字名暂不扩展为二字名。

已确认：

单字古人名不作为推荐候选，但用于构建可用字库、字频统计和文化字权重。

### 3.3 登科录：历代进士

文件：

```text
resource/登科录/古代进士名录.json
resource/登科录/古代进士名录.csv
resource/登科录/CBDB_2022.sqlite3
```

样例字段：

```json
{
  "c_personid": 363584,
  "c_name_chn_simple": "叶芾棠",
  "c_alt_name_字_简体": "",
  "c_alt_name_别号_简体": "",
  "c_alt_name_别名_曾用名_简体": "",
  "c_dynasty_chn": "清",
  "c_year": 1905,
  "c_exam_rank": "第2甲第17名"
}
```

可提取字段：

| 字段                               | 含义         | 用途               |
| ---------------------------------- | ------------ | ------------------ |
| c_personid                         | CBDB 人物 ID | 来源引用           |
| c_name_chn_simple                  | 简体姓名     | 取姓名尾二字       |
| c_alt_name_字_简体                 | 字           | 候选名             |
| c_alt_name_别号_简体               | 别号         | 第一版不参与候选，仅保留来源记录 |
| c_alt_name_别名_曾用名_简体        | 曾用名/别名  | 第一版不参与候选，仅保留来源记录 |
| c_dynasty_chn / c_dynasty_chn_登科 | 朝代         | 来源解释、古旧程度 |
| c_year                             | 登科年份     | 来源解释           |
| c_exam_rank                        | 科考成绩     | 来源质量说明       |

提取策略：

1. `c_name_chn_simple` 清洗后长度为 3 或 4 时，取最后二字作为候选。
2. `c_alt_name_字_简体` 按 `/` 拆分，长度为 2 的条目作为候选。
3. `c_alt_name_别号_简体` 第一版不启用为候选，只保留在来源记录中，便于后续审计。
4. `c_alt_name_别名_曾用名_简体` 第一版不启用为候选，只保留在来源记录中。
5. 保留人物 ID、朝代、年份、科考成绩作为解释字段。

已确认：

登科录第一版只有姓名尾二字和「字」参与候选；别号、曾用名暂不参与候选。


### 3.4 科研/院士/基金负责人：五道口

文件：

```text
resource/science/科学院院士名录.txt
resource/science/工程院院士名录.txt
resource/science/国家自然基金_项目负责人_截至2017.txt
resource/science/国家社科基金_项目负责人_截至202305.txt
resource/science/汇总.txt
```

样例：

```text
左铁镛
邹学校
庄惟敏
```

可提取字段：

| 字段        | 含义     | 用途                         |
| ----------- | -------- | ---------------------------- |
| line        | 每行姓名 | 取姓名尾二字                 |
| source file | 来源文件 | 区分院士、自然基金、社科基金 |

提取策略：

1. 每行清洗为中文姓名。
2. 长度为 3 或 4 时取最后二字作为候选。
3. 长度为 2 时需判断是否为复姓或二字姓名，第一版可先跳过。
4. 院士名录权重高于普通项目负责人。
5. 分别读取四个细分文件并保留来源层级；`汇总.txt` 只作为校验参考，不参与计数，避免和单独文件重复。

### 3.5 基金与公司名：财富论

文件：

```text
resource/fund_db/原始数据/私募基金管理公司名称_截至20230507.json
resource/fund_db/原始数据/已公布私募基金名_截至20230507.json
resource/fund_db/解析结果/基金名_分词_词频统计结果.json
```

样例：

```json
"柔微－星火燎原1号资产管理计划"
"Oaktree(北京)投资管理有限公司"
```

分词结果样例：

```json
{
  "content": "投资",
  "count": 190963
}
```

可提取字段：

| 字段         | 含义         | 用途            |
| ------------ | ------------ | --------------- |
| 原始基金名   | 基金产品名称 | 分词、来源解释  |
| 原始公司名   | 管理公司名称 | 分词、来源解释  |
| 分词 content | 分词片段     | 候选二字词      |
| 分词 count   | 出现次数     | 精选/集思录分层 |

提取策略：

1. 优先使用已有 `基金名_分词_词频统计结果.json`，避免每次都跑分词。
2. 若需要重新分词，则使用 `nodejieba` 或后续确定的分词工具。
3. 只取长度为 2 的中文片段。
4. 先过滤明显高频通用词、停用词、非人名词，再参与频率分层。
5. 清洗后的二字词按出现频率降序排序，前 10% 作为 `财富论-精选集`。
6. 清洗后的其余 90% 作为 `财富论-集思录`。
7. 需要维护非人名词表，过滤“视频、蜂巢、帮扶、轻盐、熵零”等明显产品词或普通词。
8. 基金名和公司名不拆成两个最终来源，统一归入财富论；但 `sourceDetail` 需要保留 `fund_name` 或 `company_name`，方便后续分析。
9. 实现上优先复用旧脚本逻辑，对基金名和公司名统一分词、合并统计；已有 `基金名_分词_词频统计结果.json` 可作为校验和性能优化参考。

已确认：

1. 财富论不再强制沿用旧的 `3 <= count < 300` / `1-2` 固定阈值，第一版改为清洗后按频率前 10% / 后 90% 分层。
2. 公司名和基金名不拆成两个最终来源，权重相同。

## 6. 数据源适配器规范

每个数据源适配器应暴露统一接口。

```ts
type DataSourceAdapter = {
  sourceId: string;
  sourceLabel: string;
  inputFiles: string[];
  buildRecords(context: BuildContext): Promise<NormalizedSourceRecord[]>;
  extractTokens(records: NormalizedSourceRecord[], context: BuildContext): Promise<ExtractedNameToken[]>;
};
```

适配器必须遵守：

1. 只读取 `resource/`。
2. 不直接写最终候选库。
3. 不吞掉异常数据，无法处理的记录写入 `rejected_tokens.json` 或 `rejects`。
4. 每个 token 必须能追溯到 `sourceRef`。
5. 每个来源必须有 README 或注释说明提取规则。

## 7. 校验规范

数据生成后必须做校验。

### 7.1 来源记录校验

1. 每条记录有 `id`。
2. 每条记录有 `sourceId`。
3. 每条记录能定位到原始文件和 `rawIndex`。
4. 字段缺失不报错，但要归一为空值。

### 7.2 候选片段校验

1. token 必须为 2 个中文字符。
2. token 必须能在字库中找到两个字。
3. token 不应包含多音风险字，除非在主动定音表中。
4. token 必须有至少一个来源引用。
5. token 的 reject reason 必须可枚举。

### 7.3 候选名库校验

1. 无重复 `name`。
2. 无缺字候选。
3. 无长度异常候选。
4. 来源统计和候选统计一致。
5. 样例回归可解释：
   - 正向：姚瑾瑞、钱弘俶、尧歌游。
   - 反向：赵钱孙、刘强、李建国。

## 8. 新数据源接入流程

新增数据源时按以下流程：

1. 把原始数据放入 `resource/<source_name>/`。
2. 在 `api/database/source/source_manifest.json` 中登记来源。
3. 新增 `scripts/data/adapters/<source_name>.ts`。
4. 适配器输出标准 `NormalizedSourceRecord`。
5. 适配器输出标准 `ExtractedNameToken`。
6. 在 `scripts/data/buildAll.ts` 中注册适配器。
7. 运行 `data:build`。
8. 运行 `data:validate`。

### 11.6 数据源处理规则摘要

1. 他山石：读取 `resource/person_name/已知人名.json`，`length === 2` 的 name 作为二字候选；单字只计入字频。
2. 古人云：读取 `resource/old_person_name/中国古代人名与字-9336条-简体-opencc转换稿_手工替换_乾干.json`，二字 `char_名` 和二字 `char_字` 作为候选；单字只计入字频。
3. 登科录：读取 `resource/登科录/古代进士名录.json`，姓名尾二字和二字「字」作为候选；别号、曾用名第一版只保留来源记录，不参与候选。
4. 五道口：读取 `resource/science/` 下四个细分文件，保留来源层级；`汇总.txt` 只作为校验参考，不参与重复计数。

### 11.7 质量约束

1. 候选名必须是二字中文。
2. 候选名中的两个字必须存在于字库。
3. 多音字默认过滤，除非在主动定音表中。
4. 每个候选必须至少有一个 `sourceRef`，能追溯到原始数据文件、记录下标和字段。
5. 被拒绝的候选必须进入 `rejected_tokens.json`，并记录枚举化拒绝原因。
6. 单字名不推荐，但必须参与字频和字权重。
7. 非人名词、产品词、过泛词需要通过规则或词表过滤。
