# 数据处理规划

本文档用于规划如何从 `resource/` 中的原始数据生成 `database/` 中可被推荐系统使用的 JSON 数据。

目标不是一次性写死某个脚本，而是建立一套可扩展的数据处理规范：后续新增数据源时，只需要补一个数据源适配器和少量配置，就能进入统一候选名库。

约定：

- `@todo(yao)` 表示需要 yao 确认、取舍或补充的信息。
- 原始数据保留在 `resource/`，不移动、不覆盖。
- 清洗结果输出到 `database/`。
- 脚本优先使用 TypeScript 编写，执行方式优先使用 `tsx`。@todo(yao) 是否确认后续新增 `tsx` 作为开发依赖，并统一用 `tsx scripts/...` 执行数据脚本？

## 1. 要解决的问题

当前第一版候选库是从 `old/database` 生成的，这能快速验证推荐流程，但长期不够理想。

真正的数据管线应该是：

```text
resource 原始数据
  -> source adapter 按来源解析
  -> normalized source records 标准化来源记录
  -> extracted name tokens 抽取二字候选
  -> candidate name db 统一候选名库
  -> query / score / explain 推荐系统使用
```

这套流程需要解决四件事：

1. 我们需要哪些字段。
2. 从 `resource/` 中可以提取哪些字段。
3. 每类数据源如何编写提取脚本。
4. 如何编订规范，方便后续补充新数据。

## 2. 输出数据分层

建议不要直接从原始数据一步生成最终候选名库，而是分三层输出。

### 2.1 来源记录层

目录建议：

```text
database/source/
  source_manifest.json
  wealth.records.json
  academic.records.json
  modern_people.records.json
  imperial_exam.records.json
  ancient_names.records.json
```

作用：

1. 保存每条原始记录的标准化结果。
2. 保留来源索引，便于回溯候选名为什么出现。
3. 为后续解释、审计和重新生成候选名提供依据。

建议字段：

```ts
type NormalizedSourceRecord = {
  id: string;
  sourceId: string;
  sourceLabel: string;
  sourcePath: string;
  rawIndex: number;
  rawText?: string;
  rawFields?: Record<string, unknown>;
  normalizedFields: Record<string, string | number | string[] | null>;
  extractedTexts: ExtractedText[];
};

type ExtractedText = {
  text: string;
  textType:
    | "person_full_name"
    | "given_name"
    | "courtesy_name"
    | "alias"
    | "fund_name"
    | "company_name"
    | "word_segment"
    | "science_person_name";
  confidence: number;
  note?: string;
};
```

2. 记录候选来自哪些来源、出现多少次、如何抽取。
3. 记录被拒绝的数据及原因，方便调规则。

### 3.1 现代姓名：他山石

```json
{
  "木尔": {
    "name": "木尔",
    "counter": 1,
```

可提取字段：

| 字段       | 含义               | 用途         |

3. 经过字库合法性、多音字、音律规则过滤。
4. 输出为 `modern_given_name`。

## 6. 数据源适配器规范

每个数据源适配器应暴露统一接口。

```ts
type DataSourceAdapter = {
  sourceId: string;
  sourceLabel: string;
  inputFiles: string[];
  buildRecords(context: BuildContext): Promise<NormalizedSourceRecord[]>;
  extractTokens(records: NormalizedSourceRecord[], context: BuildContext): Promise<ExtractedNameToken[]>;
};
```

适配器必须遵守：

1. 只读取 `resource/`。
2. 不直接写最终候选库。
3. 不吞掉异常数据，无法处理的记录写入 `rejected_tokens.json` 或 `rejects`。
4. 每个 token 必须能追溯到 `sourceRef`。
5. 每个来源必须有 README 或注释说明提取规则。

## 7. 校验规范

数据生成后必须做校验。

### 7.1 来源记录校验

1. 每条记录有 `id`。
2. 每条记录有 `sourceId`。
3. 每条记录能定位到原始文件和 `rawIndex`。
4. 字段缺失不报错，但要归一为空值。

### 7.2 候选片段校验

1. token 必须为 2 个中文字符。
2. token 必须能在字库中找到两个字。
3. token 不应包含多音风险字，除非在主动定音表中。
4. token 必须有至少一个来源引用。
5. token 的 reject reason 必须可枚举。

### 7.3 候选名库校验

1. 无重复 `name`。
2. 无缺字候选。
3. 无长度异常候选。
4. 来源统计和候选统计一致。
5. 样例回归可解释：
   - 正向：姚瑾瑞、钱弘俶、尧歌游。
   - 反向：赵钱孙、刘强、李建国。

## 8. 新数据源接入流程

新增数据源时按以下流程：

1. 把原始数据放入 `resource/<source_name>/`。
2. 在 `database/source/source_manifest.json` 中登记来源。
3. 新增 `scripts/data/adapters/<source_name>.ts`。
4. 适配器输出标准 `NormalizedSourceRecord`。
5. 适配器输出标准 `ExtractedNameToken`。
6. 在 `scripts/data/buildAll.ts` 中注册适配器。
7. 运行 `data:build`。
8. 运行 `data:validate`。
9. 检查 `rejected_tokens.json`。
10. 抽查 Top 30 推荐结果。

## 9. 第一阶段实施建议

建议按这个顺序做：

1. 先定义 TypeScript 类型：`NormalizedSourceRecord`、`ExtractedNameToken`、`CandidateNameRecord`。
2. 建立 `scripts/data/lib/` 公共工具。
3. 先接入最简单的三个来源：
   - `modernPeople`
   - `ancientNames`
   - `sciencePeople`
4. 再接入 `imperialExam`。
5. 最后处理最复杂的 `wealthWords`。
6. 输出 `database/source/`、`database/extracted/`、`database/candidate/`。
7. 用当前 CLI 验证推荐结果。

原因：

1. 现代姓名、古人名、科研姓名都是「姓名类数据」，抽取规则简单。
2. 登科录字段多，但结构化程度高。
3. 财富论涉及分词和非人名词过滤，最容易影响推荐质量，应该最后调。
